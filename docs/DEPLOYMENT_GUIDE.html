      Deployment guide

      Marchmaker Deployment Guide

      Put the member site and the admin console on Vercel, and the API and background worker on Render. Every account to open, every value to copy and every button to press is listed in the order you need it.

      Start here Overview

      Read this page once before you touch anything. It shows what runs where and why the order of the steps matters.

      What runs where

      PartRuns onAddress (example names)
      Member siteVercel project marchmaker-webhttps://marchmaker-web.vercel.app
      Admin consoleVercel project marchmaker-adminhttps://marchmaker-admin.vercel.app
      APIRender Web Service marchmaker-apihttps://marchmaker-api.onrender.com
      Background worker (photos, email, matching, invoices)Render Background Worker marchmaker-workerNo public address
      Job queueRender Key Value (Redis) marchmaker-redisPrivate address inside Render
      DatabaseMongoDB AtlasConnection string
      Photos, ID images, exports, invoicesCloudflare R2 (three private buckets)S3-compatible address
      Email, SMS, payments, error reportsResend, MSG91, Razorpay, SentryTheir dashboards

      How a request travels

      1. Browser
      2. →
      3. Vercel (site files)
      4. →
      5. /api/… forwarded by Vercel
      6. →
      7. Render API
      8. →
      9. MongoDB · Redis · R2

      The sites call /api/v1/… on their own address. Vercel forwards those calls to the Render API. To the browser everything is one website, so sign-in cookies work without any cross-site settings. The forwarding rule lives in apps/web/vercel.json and apps/admin/vercel.json.

      The order of work

      1. Open the outside accounts and collect their keys (sections 1 and 4 to 9).
      2. Put the code on GitHub (section 2).
      3. Create the secrets (section 3).
      4. Create Redis, the shared settings, the API and the worker on Render (sections 10 to 13).
      5. Prepare the empty database and create the first admin (section 14).
      6. Point the Vercel files at your API, then create the two Vercel projects (sections 15 to 17).
      7. Connect everything together and test (sections 18 and 19).
      The API refuses to start with test settings

      In production the API checks its own settings and stops with a list of what is wrong. It will not start with test email, test SMS, test payments, development secrets, local file storage, no Redis, or no error reporting. That is on purpose. It means every account in section 1 is needed before the first successful start.

      What is already prepared in the code

      While preparing this guide I fixed things that would have stopped a first deployment. They are committed in both repos:

      • Docker builds that work. The old API and worker Dockerfiles could not build a runnable image. They now bundle the shared packages and install only production dependencies.
      • The frontend builds on its own. It used to read a package from a folder in the backend repo, which does not exist on Vercel. A copy now lives in packages/shared. A script keeps it in step with the backend (section 2).
      • Data exports use object storage. They were written to one machine's disk and read from another's, which cannot work on Render. They now live in the documents bucket.
      • Client address behind two proxies. A new setting, TRUST_PROXY_HOPS, makes rate limits count real visitors and not Vercel's address.
      • Vercel settings for both sites, including the API forwarding rule and security headers.

      I could not run Docker or Render on this computer. The Docker files were checked by building the same bundles and starting them with a production-style install, but the first real build happens on Render. Section 22 lists the likely first-build problems.

      2. Put the code on GitHub Prepare

      Render and Vercel build from the main branch. Right now the latest work is on other branches.

      Check this first

      The fixes described in the overview exist only on local branches (dev-local-testing in the backend and google-signin in the frontend). Until they are merged and pushed to main, a deployment would build the old code and fail.

      1. Backend. In a terminal:
        Terminal
        cd marchmaker_backend
git status
git checkout main
git merge --ff-only dev-local-testing
git push origin main
        Result: the push succeeds. If the merge says it cannot fast-forward, someone changed main in between. Ask for help before forcing anything.
      2. Frontend.
        Terminal
        cd ../marchmaker_frontend
git status
git checkout main
git merge --ff-only google-signin
git push origin main
      3. Check both repos on github.com. The latest commit on main should mention the deployment changes.

      Keeping the shared package in step

      The frontend keeps its own copy of the backend's shared package. Whenever the backend's packages/shared changes, update the copy and commit it. Keep the two repos next to each other in one folder for this.

      In marchmaker_frontend
      pnpm sync:shared     # copy from the backend
pnpm check:shared    # fails if the copy is out of date
      Two leftover folders you can delete

      While testing the Docker bundles I created two temporary folders beside the repos: _deploy_tmp and _deploy_tmp2. They are not part of either repo and are safe to delete.

      3. Create your secrets Prepare

      These values protect your members' data. Generate them yourself, once, and save them in a password manager.

      Terminal (needs Node.js)
      # 1 and 2: the two session secrets (run twice, use each result once)
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

# 3 and 4: the encryption key and the lookup key (run twice, use each result once)
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"

# 5: the Razorpay webhook secret (any long random string)
node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"
      NameWhat it doesIf you lose or change it
      JWT_ACCESS_SECRETSigns short sign-in tokens.Everyone is signed out. No data is lost.
      JWT_REFRESH_SECRETSigns long sign-in tokens and email links.Everyone is signed out and old links stop working.
      FIELD_ENCRYPTION_KEYEncrypts birth dates, phone numbers and other private fields.Encrypted data becomes unreadable for ever. Back it up.
      FIELD_BLIND_INDEX_KEYLets the system find a phone number without storing it in the clear.Never change it. Existing phone numbers stop matching.
      RAZORPAY_WEBHOOK_SECRETProves payment notices come from Razorpay.Set the same value in Razorpay again.
      Never share or commit these

      Do not paste them into chat, email or a file in the repo. Render and Vercel store them for you. Put a copy only in your password manager.

      4. MongoDB Atlas Accounts

      The database. The app needs a replica set (transactions), which every Atlas cluster is.

      1. Sign in at cloud.mongodb.com and create a project named marchmaker.
      2. Create a cluster. Pick M10 or larger for real use (it includes backups) or the free M0 for a trial. Choose a provider and a region close to your Render region. AWS Mumbai (ap-south-1) is a good match for India.
      3. Create a database user. Under Database Access add a user named marchmaker_app with a long random password. Give it the built-in role Read and write to any database or, better, restrict it to the database marchmaker.
      4. Allow Render to connect. Under Network Access choose one:
        • Simplest: add 0.0.0.0/0 (anywhere). The connection is encrypted and needs the password, but anyone who gets the password could use it.
        • Tighter: after you create the Render services (sections 12 and 13) open each service, find its Outbound addresses, and add them here. Do this only if you are comfortable with the extra steps.
      5. Copy the connection string. Press Connect, then Drivers. It looks like the line below. Replace the password and add the database name marchmaker before the ?:
        Example
        mongodb+srv://marchmaker_app:YOUR-PASSWORD@cluster0.abcde.mongodb.net/marchmaker?retryWrites=true&w=majority
        Result: you have one string. This is MONGODB_URI. If the password has symbols such as @ or #, replace each with its percent code (%40, %23) or choose a password with only letters and digits.
      6. On a paid cluster open Backup and confirm automated backups are on.

      5. Cloudflare R2 storage Accounts

      Three private buckets hold photos, ID images, and documents such as exports and invoices. You can use Amazon S3 instead. See the note at the end.

      No storage account yet? Keep pictures in MongoDB

      For a trial or a small site you can skip this whole section. In the Render group set STORAGE_PROVIDER=mongo and PUBLIC_API_URL=https://your-api.onrender.com (your real API address), and leave out every S3_* value. Photos, ID images, invoices and data exports are then saved inside your MongoDB database, and every image shows. The database grows with each picture (the free Atlas plan holds 512 MB), so move to R2 or S3 before you have many members. Files uploaded from your own computer can be copied across with pnpm --filter @marchmaker/api storage:copy-local -- --to=mongo.

      1. Sign in to dash.cloudflare.com, open R2 Object Storage and enable it.
      2. Create three buckets with these exact names, a location hint of Asia-Pacific, and the default private setting. Never turn on public access.
        • marchmaker-photos
        • marchmaker-identity
        • marchmaker-documents
      3. Note your account address. On the R2 overview page copy the S3 API address. It looks like https://ACCOUNT_ID.r2.cloudflarestorage.com. This is S3_ENDPOINT.
      4. Create the general access key. Open Manage API tokens, create a token with permission Object Read & Write, limited to the buckets marchmaker-photos and marchmaker-documents. Copy the Access Key ID and Secret Access Key. They are shown once. These are S3_ACCESS_KEY_ID and S3_SECRET_ACCESS_KEY.
      5. Create the identity access key. Make a second token with Object Read & Write limited only to marchmaker-identity. These are S3_IDENTITY_ACCESS_KEY_ID and S3_IDENTITY_SECRET_ACCESS_KEY. This keeps ID images behind a separate key.
      6. Allow uploads from your sites. Members' browsers upload straight to the buckets, so each bucket needs a CORS rule. For each of the three buckets open Settings, then CORS policy, and paste this. Use your real site addresses:
        CORS policy for all three buckets
        [
  {
    "AllowedOrigins": [
      "https://marchmaker-web.vercel.app",
      "https://marchmaker-admin.vercel.app"
    ],
    "AllowedMethods": ["GET", "PUT", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
        Result: three buckets, two key pairs and one address. If your sites later move to your own domain, come back and add those addresses (section 20).
      Using Amazon S3 instead

      Create the same three buckets in an AWS region such as ap-south-1, create IAM users with read and write on them, and set S3_REGION=ap-south-1. Leave S3_ENDPOINT unset. Add the same CORS rules in each bucket's permissions.

      6. Email with Resend Accounts

      Sign-up confirmations, password resets, notices and invoices all go through Resend.

      1. Create an account at resend.com.
      2. Add your domain. Open Domains, press Add Domain and enter a domain you own, for example mail.yourdomain.com (a sub-domain keeps your main mail safe).
      3. Add the DNS records. Resend shows a short table of records. Add each one at the company where you bought the domain (its DNS settings page). Wait until Resend shows the domain as Verified. This can take from minutes to a few hours.
      4. Create an API key. Open API Keys, create one with Sending access, and copy it. This is RESEND_API_KEY.
      5. Choose the sender. It must use the verified domain, for example Marchmaker <hello@mail.yourdomain.com>. This is EMAIL_FROM. Pick a real support address you read for SUPPORT_EMAIL.
      6. The webhook comes later (section 18), once the API has an address.

      7. SMS with MSG91 Accounts

      One-time codes for phone sign-in go by SMS. Indian carriers only deliver messages that use a registered template.

      1. Create an account at msg91.com and complete the business verification.
      2. Register on DLT with the telecom operator portal MSG91 points you to. Register your company, a sender ID and a content template for the code message. MSG91's support pages walk through this.
      3. In MSG91 create an OTP template (a “flow”) that uses your approved DLT template. The code goes in as a variable.
      4. Copy your Auth Key (this is MSG91_AUTH_KEY) and the Template ID of the OTP flow (this is MSG91_OTP_TEMPLATE_ID).
      Check the final wording

      The exact screens and field names at MSG91 change over time. Follow their current instructions where they differ from this list. The two values you need are always the Auth Key and the Template ID.

      8. Payments with Razorpay Accounts

      Start in test mode so you can try every payment without moving money.

      1. Create an account at razorpay.com. Stay in Test mode (the switch in the dashboard header).
      2. Open Account & Settings, then API Keys, and generate a key. Copy the Key Id (rzp_test_…) and the Key Secret. These are RAZORPAY_KEY_ID and RAZORPAY_KEY_SECRET. The Key Id is also needed on the member site (VITE_RAZORPAY_KEY_ID).
      3. The webhook comes later (section 18), once the API has an address. You will use the secret you generated in section 3.
      4. To take real money later, complete Razorpay's business verification, switch to live mode, generate live keys and replace the three values.
      Prefer Stripe? It works as an alternative

      Set PAYMENTS_PROVIDER=stripe instead of the Razorpay values, and add STRIPE_SECRET_KEY (the sk_test_… key) and STRIPE_WEBHOOK_SECRET. Members pay on Stripe's own page, so the browser needs no Stripe key. In Stripe, open Developers, then Webhooks, add the endpoint https://your-api.onrender.com/api/v1/webhooks/stripe with the events checkout.session.completed, checkout.session.async_payment_succeeded, checkout.session.async_payment_failed, invoice.paid, customer.subscription.updated, customer.subscription.deleted and charge.refunded, then copy its signing secret (whsec_…). Switch on the Customer portal (Settings, then Billing) so members can update their card. In test mode pay with card 4242 4242 4242 4242, any future date and any 3 digits.

      9. Error reports with Sentry Accounts

      The API will not start without a Sentry address, so crashes are never invisible.

      1. Create an account at sentry.io and an organization.
      2. Create a project, platform Node.js, called marchmaker-backend. Copy its DSN (a web address starting with https://). This is SENTRY_DSN for the API and the worker.
      3. Optionally create a second project, platform React, called marchmaker-web, and copy its DSN for VITE_SENTRY_DSN on Vercel.

      Optional: Google sign-in

      Follow section 6.5 of the Testing Guide to create a Google web client. You add your two Vercel addresses (and later your own domains) as Authorized JavaScript origins, and set GOOGLE_CLIENT_ID in the shared settings below. Publish the consent screen so every Google user can sign in, not only test users.

      10. Render: Redis Render

      The job queue and shared rate limits. Create it first, because the API and worker need its address.

      1. Sign in at dashboard.render.com and connect your GitHub account under Account Settings if you have not.
      2. Press New +, then Key Value (Render's Redis-compatible store).
      3. Name it marchmaker-redis. Choose the region you will use for everything (for India, Singapore is the closest). Remember it, because all Render services must be in the same region.
      4. Choose a plan: Free for a trial (data is lost on restart), or Starter or larger for real use.
      5. Set the Maxmemory Policy to noeviction. The job queue needs this so jobs are never dropped.
      6. Under access control keep it private (allow only your Render services; add no outside addresses).
      7. Press Create Key Value. When it is ready open it and copy the Internal Connection URL. It looks like redis://red-abc123:6379. This is REDIS_URL.

      If the free plan loses its data on a restart, queued jobs disappear from Redis. Events are stored in the database first and re-sent, so nothing is lost, but the paid plan avoids delays.

      1. In the dashboard press New +, then Web Service.
      2. Choose Build and deploy from a Git repository, then select marchmaker_backend. If it is not listed, press Configure account and give Render access to that repo.
      3. Fill in the form:
        FieldValue
        Namemarchmaker-api
        RegionThe same region as Redis
        Branchmain
        Language / RuntimeDocker
        Root DirectoryLeave blank (the repo root)
        Instance typeStarter or larger
      4. Open Advanced and set:
        FieldValue
        Dockerfile Path./apps/api/Dockerfile
        Docker Build Context Directory.
        Health Check Path/healthz
        Auto-DeployOn Commit
      5. Attach the settings. Under Environment find Linked Environment Groups and link marchmaker-shared. You do not need to add PORT. Render sets it and the API reads it.
      6. Press Create Web Service. The first build takes several minutes. Watch the Logs tab. Result: the log ends with mongo connected and api listening, and the service shows Live.

      That line lists exactly which settings are wrong, for example a missing Redis address or Sentry address. Fix them in the environment group, then use Manual Deploy and Clear build cache & deploy if needed. Other likely problems are in section 22.

      The worker processes photos, sends emails, runs matching and draws invoices. Without it, photos stay on “Processing…”.

      1. Press New +, then Background Worker.
      2. Select the same repo marchmaker_backend, branch main.
      3. Fill in:
        FieldValue
        Namemarchmaker-worker
        RegionSame as the API and Redis
        RuntimeDocker
        Instance typeStarter or larger (no free plan exists for workers)
        Dockerfile Path./apps/worker/Dockerfile

      4. Link the same environment group marchmaker-shared.
      5. Press Create Background Worker. Result: the log shows the worker connected to MongoDB and started its job loop, with no “Refusing to start” line. Also check Redis shows as connected, not an error repeating.

      14. Prepare the database and create the first admin Render

      Run these three commands once from your own computer. They fill the empty production database with the legal texts, plans, question banks and your first super admin.

      Use the same keys as Render

      The commands below encrypt the admin's birth date. The FIELD_ENCRYPTION_KEY and FIELD_BLIND_INDEX_KEY you type here must be exactly the ones in the Render environment group. A different key makes that data unreadable by the live app.

      1. Open a terminal in marchmaker_backend and make sure the packages are installed (pnpm install).
      2. Set the values for this terminal only. Pick the admin email you will really use, and a long unique password of at least 12 characters.
        Windows PowerShell
        $env:MONGODB_URI='PASTE-THE-SAME-CONNECTION-STRING'
$env:FIELD_ENCRYPTION_KEY='PASTE-THE-SAME-KEY'
$env:FIELD_BLIND_INDEX_KEY='PASTE-THE-SAME-KEY'
$env:SEED_ADMIN_EMAIL='you@yourdomain.com'
$env:SEED_ADMIN_PASSWORD='a-long-unique-password'
        macOS / Linux / Git Bash
        export MONGODB_URI='PASTE-THE-SAME-CONNECTION-STRING'
export FIELD_ENCRYPTION_KEY='PASTE-THE-SAME-KEY'
export FIELD_BLIND_INDEX_KEY='PASTE-THE-SAME-KEY'
export SEED_ADMIN_EMAIL='you@yourdomain.com'
export SEED_ADMIN_PASSWORD='a-long-unique-password'
      3. Run the three commands in order:
        Terminal
        pnpm --filter @marchmaker/api migrate:up
pnpm --filter @marchmaker/api sync-indexes
pnpm --filter @marchmaker/api seed
        Result: migrate:up lists migrations applied (it may say there is nothing to migrate on a new database). sync-indexes prints “indexes ensured”. seed prints “super admin ensured; two-factor setup is required at first sign-in”.
      4. Clear the secrets from the terminal by closing it. In PowerShell you can also run Remove-Item Env:MONGODB_URI, Env:FIELD_ENCRYPTION_KEY, Env:FIELD_BLIND_INDEX_KEY, Env:SEED_ADMIN_PASSWORD.
      Do not run the demo seed here

      seed:demo refuses to run in production, and fake members have no place in a live database.

      15. Point the sites at your API Vercel

git commit -m "Point Vercel at the Render API"
git push origin main

      17. Vercel: the admin console Vercel

      A second project from the same repo.

      18. Connect everything Wire up

      Now that every address exists, finish the pieces that needed them.

      18.1 Confirm the three addresses

      1. Compare the real Vercel addresses with APP_URL, ADMIN_URL and CORS_ORIGINS in the Render environment group. If any differ, edit them, then press Save. Render redeploys the API and worker when the group changes. If it does not, use Manual Deploy on both.
      2. Check the R2 CORS rules (section 5) and the Google origins (section 9) list the same real addresses.

      18.2 Razorpay webhook

      1. In Razorpay open Account & Settings, then Webhooks, and add a webhook.
      2. URL: https://marchmaker-api.onrender.com/api/v1/webhooks/razorpay. This goes straight to Render, not through Vercel. Use your real Render address.
      3. Secret: the RAZORPAY_WEBHOOK_SECRET from section 3, exactly.
      4. Tick the events: all payment.*, order.paid, all subscription.* and all refund.*. Save.

      18.3 Resend webhook

      1. In Resend open Webhooks and add an endpoint: https://marchmaker-api.onrender.com/api/v1/webhooks/resend. Tick the delivery events (delivered, bounced, complained).
      2. Resend shows a signing secret. Copy it, replace the temporary RESEND_WEBHOOK_SECRET in the Render group with it, and save. The webhook lets the app stop emailing addresses that bounce or complain.

      19.1 First admin sign-in with two-factor

      2. Open the admin console address and sign in with the admin email and password from section 14. Result: a setup page with a QR code.

      21. Day to day Operate

      Releasing a change

      • Backend change: push to main. Render rebuilds and swaps the API and the worker automatically. If the change adds a database migration, run migrate:up and sync-indexes from your computer (section 14, first two commands) before pushing.
      • Frontend change: push to main. Vercel rebuilds both projects. If the backend's shared package changed, run pnpm sync:shared in the frontend first and commit it.
      • Settings change: edit the Render environment group. Render redeploys both services.

      Rolling back

      • Render: open the service, then Events, and pick an earlier successful deploy to roll back to.
      • Vercel: open the project, then Deployments, choose an earlier one and press Promote to Production.
      • A database migration is not undone by a code rollback. Read the migration before relying on it.

      Where to look when something is wrong

      • Render service, Logs (live) and Metrics.
      • Vercel project, Deployments, then Logs and the build output.
      • Sentry for errors, Atlas Metrics for the database, Resend Logs for email, Razorpay Webhooks for payment notices.
      • The admin console's Jobs and providers, Payment webhooks and Audit log pages.
      • docs/RUNBOOK.md in the backend repo for incidents, alerts and the backup restore drill.

      Good habits

      • Keep the API on a paid plan so it never sleeps. On a free plan the first visit after a quiet period takes about a minute.
      • Turn on Atlas backups and do one restore drill before launch.
      • Store all keys in a password manager. The two that cannot be recovered are FIELD_ENCRYPTION_KEY and FIELD_BLIND_INDEX_KEY.
      • Rotate the Razorpay, Resend and R2 keys if anyone who knew them leaves.

      22. If something goes wrong Help

      What you seeWhy, and what to do
      Render build fails at pnpm install --frozen-lockfileThe lockfile does not match a package.json. Run pnpm install in the backend repo, commit the changed pnpm-lock.yaml and push.
      Render build fails with an out-of-memory errorUse a larger build instance or retry. The workspace install is large.
      API log: “Refusing to start in production: …”Read the list after the colon. Each item names the setting to fix in the environment group.
      API log: “Invalid environment: …”A value has the wrong shape, for example FIELD_ENCRYPTION_KEY is not base64, or a setting is empty. Delete empty settings.
      API or worker cannot connect to MongoDBCheck Network Access in Atlas, the user and password, and that special characters in the password are percent-encoded.
      API log: cannot connect to RedisUse the Internal URL, and keep Redis and both services in the same region.
      The member site shows a Vercel error or 502 on /api/…The API is asleep (free plan), crashed, or the address in vercel.json is wrong. Open the API's /healthz directly. Fix the address, push, and Vercel redeploys.
      Page loads but you cannot sign in or registerCheck COOKIE_SECURE=true, and that CORS_ORIGINS, APP_URL and ADMIN_URL match your site addresses exactly (https, no trailing slash). A 403 saying the origin is not allowed means a mismatch.
      Everyone gets “too many attempts” or rate limitsThe API sees one address for all visitors. Set TRUST_PROXY_HOPS=2 and redeploy.
      Photo upload fails in the browserThe bucket CORS rule is missing or does not list your site address (section 5).
      Photo stays on “Processing…”The worker is not running, cannot reach Redis, or uses different storage settings. Check its logs and that it links the same environment group.
      Emails never arriveThe sending domain is not verified in Resend, EMAIL_FROM uses a different domain, or the message went to spam. Look at Resend's Logs.
      SMS codes never arriveThe DLT template is not approved or the template ID is wrong. Check MSG91's delivery report.
      Payment completes but credits do not appearThe Razorpay webhook is wrong. Compare the address and the secret, and look at the admin Payment webhooks page.
      Vercel build: “cannot find @marchmaker/shared”The shared copy is missing. Make sure packages/shared is committed, and that Include source files outside of the Root Directory is on.
      Vercel build fails with a type error about a shared typeThe frontend copy is out of date. Run pnpm sync:shared in the frontend, commit and push.
      Admin says two-factor setup is required but the page is stuckSign out and sign in again. An old session from before enrolment has no code check.
      Data export downloads failThe documents bucket key lacks write access, or the worker cannot reach storage. Check the worker log.
