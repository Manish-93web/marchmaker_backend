      Tester guide

      Marchmaker Testing Guide

      Marchmaker is a subscription service that makes a small number of human-reviewed marriage introductions in India. This guide takes you from an empty computer to a finished introduction between two members, and lists everything else worth checking along the way.

      Start here Overview

      Read this page first. It tells you what you are testing, where to open it and which logins to use.

      What the platform does

      • Members register, build a profile, upload photos, verify their ID and set preferences.
      • The admin team reviews every profile, photo and ID, and approves every match by hand.
      • Introductions are released to both people. Each says yes or no. A credit is spent only when both say yes, and then messaging opens.
      • There is no swiping and no browsing of other members.

      Purple steps are done by an admin in the admin console. Everything else is done as a member on the member site. You will need two members (one woman and one man) to see a match through.

      Rules that keep your two sign-ins apart

      • Use a separate private (incognito) window for each person you sign in as. Two member accounts in one normal window share one session and will log each other out.
      • The admin console keeps its own sign-in, so you can stay signed in to the admin console and one member at the same time.
      • Use localhost in every address. Do not switch to 127.0.0.1 for the member site.

      1. Before you start Setup

      Install these once. Allow about 30 minutes for the whole setup.

      You needVersionCheck with
      Node.js20 or newer (24 works)node -v
      pnpm9.15 (any 9.x)pnpm -v (get it with corepack enable)
      Gitany recent versiongit --version
      A MongoDB databaseMongoDB Atlas free tierCreated in the next step

      Redis and Docker are not needed. Without Redis the background worker runs jobs inside its own process, which is fine for testing.

      Create a free MongoDB Atlas database

      1. Sign up at mongodb.com/cloud/atlas and create a free M0 cluster. Choose any region.
      2. Under Database Access, add a user with a username and password. Write both down.
      3. Under Network Access, add the address 0.0.0.0/0 (allow from anywhere). This is acceptable for a throwaway test database.
      4. Press Connect, then Drivers, and copy the connection string. It looks like mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/. Result: you have one connection string. Put your own password where it says PASSWORD. Add a database name before the ?, for example /marchmaker?.
      Why Atlas and not a local MongoDB

      The app uses database transactions, which need a replica set. Atlas gives you one automatically. A plain local MongoDB does not.

      2. Set up the backend Setup

      The backend is the API plus a background worker.

      Folder names matter

      The two projects must sit next to each other in one parent folder and keep the names marchmaker_backend and marchmaker_frontend. The frontend reads a shared package from the backend folder by that path.

      1. Download the code. Make an empty folder, open a terminal in it and run:
        Terminal
        git clone https://github.com/Manish-93web/marchmaker_backend.git
git clone https://github.com/Manish-93web/marchmaker_frontend.git
        Result: two folders, marchmaker_backend and marchmaker_frontend, side by side.
      2. Install the backend packages.
        Terminal
        cd marchmaker_backend
pnpm install
pnpm --filter @marchmaker/shared build
        Result: no red errors. The last command prints a build success message.
      3. Create the settings file for the API. Make a new file called .env inside marchmaker_backend/apps/api/ with exactly this content. Replace the connection string with yours from the previous section.
        apps/api/.env
        NODE_ENV=development
MONGODB_URI=mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/marchmaker?retryWrites=true&w=majority
EMAIL_PROVIDER=mock
STORAGE_PROVIDER=local
STAFF_MFA_REQUIRED=false
      4. Copy the same file for the worker. Save the identical content as marchmaker_backend/apps/worker/.env. Result: two files with the same lines, one in apps/api and one in apps/worker.
      What each line does
      SettingMeaning
      MONGODB_URIYour database. This is the only value you must change.
      EMAIL_PROVIDER=mockNo real email is sent. The text of every email, including confirmation links, is printed in the API terminal window.
      STORAGE_PROVIDER=localUploaded photos and ID images are saved in a .data folder on your computer instead of cloud storage.
      STAFF_MFA_REQUIRED=falseThe admin signs in with email and password only, with no authenticator code. This is for testing and the app refuses to start in production with it.

      Payments, ID checks, SMS, WhatsApp and push are all simulated by default, so no keys are needed.

      Optional lines you may need
      • If the API cannot find your cluster and the error mentions ECONNREFUSED or SRV, add DNS_SERVERS=8.8.8.8,1.1.1.1.
      • Never leave a setting as NAME= with nothing after it. The app rejects empty values. Delete the line instead.
      • For Google sign-in see section 6.5.

Whenever this guide says “find the link in the API terminal”, look for a line containing mock email captured and read the text field. Text-message codes appear the same way as mock sms captured.

      Fill in the steps in order, using Next and Back. You can leave and come back later. The wizard reopens at the first unfinished step.

      7.2 Upload photos

      1. In the Photos step choose one or two clear pictures of a face.
        • File types: JPEG, PNG or WebP.
        • At least 200 × 200 pixels and no more than 10 MB each.
        • The first photo is the main photo. You can reorder later.
      2. After choosing a file the photo shows Processing…. Result: within a few seconds it changes to Awaiting review. The background worker is shrinking the picture, removing hidden location data and running an automated check.
      Stuck on “Processing…”

      The worker is not running. Check that Terminal 1 is still open and has no errors. The API and worker must use the same STORAGE_PROVIDER=local setting, which is why both .env files have it.

      7.3 Review and submit

      1. Open the last step, Review and submit. Result: it lists any step still missing. When everything is complete the Submit for review button works.
      2. Press Submit for review. Result: a message: “Submitted for review. Our team is reading your profile now. This usually takes up to 48 hours.” The profile is now locked for editing until the admin answers.

      8. Admin: approve the profile and photos Part C

      Now play the admin. Use a different browser window from the member window.

      8.1 Sign in to the admin console

      1. Open http://localhost:5174.
      2. Sign in with admin@example.com and Admin@12345. Result: the console opens on the Dashboard with a menu down the left. No authenticator code is asked for in this test setup.

      8.2 Approve the profile

      1. In the left menu choose Profile review. Rohan's profile is in the queue.
      2. Open it and read through every section.
      3. Press Approve (keyboard shortcut a). To send it back instead, press Request changes (c), pick the steps to revisit and write a short note. Result: the status changes to approved. On the member side the dashboard shows the next step: verification.

      8.3 Approve the photo

      1. Choose Photo review in the menu.
      2. Each pending photo has Approve and Reject buttons. Reject asks for a reason. Approve the photo. Result: the photo leaves the queue. Members only ever see approved photos, and other members see them blurred until an introduction allows more.

      Also try Request changes once on the profile, check the member sees the message, fix it as the member and submit again. A profile can only be edited by the member while it is a draft or has had changes requested.

      9. ID verification Part D

      This step opens only after the profile is approved. Real ID vendors are not connected, so a person at the admin console checks the pictures by hand.

      9.1 Member uploads the documents

      1. As Rohan, refresh the dashboard and press Verify your identity (or open /verification).
      2. Choose the ID type (Aadhaar masked, PAN card, Passport, Driving licence or Voter ID) and enter the last 4 characters of the number. The full number is never asked for.
      3. Upload the front of the ID, then the back. Use any JPEG, PNG or WebP image from 2 KB to 8 MB. A photo of any card or even a plain picture is fine for a test. Result: each box shows a green “done” mark. (The file chooser goes back to “No file chosen”. That is normal. Look for the green mark.)
      4. Selfie. Press Open camera, or Upload a photo instead if there is no camera.
      5. When all three show done, press Submit for verification. Result: the page says your verification is being reviewed, usually within 24 hours.

      9.2 Admin reviews

      1. In the admin console open Verification. Open Rohan's case.
      2. Look at the front, back and selfie. Tick the checklist items you agree with:
        • Name matches the profile
        • Date of birth matches
        • Selfie matches the document photo
        • Document is not expired
        • Document looks genuine
      3. Press Approve. You can also Reject or ask for a re-upload of specific items. Result: on the member side the ID badge is earned and the journey moves to Matching. Every view of an ID image by staff is logged.
      Privacy

      ID images are kept apart from profile photos, only the verification team can open them, and they are deleted 30 days after a decision.

      10. Preferences and assessments Part E

      The matching engine needs to know what each person is looking for.

      10.1 Set preferences

      1. As Rohan open the dashboard and press Your preferences (/preferences).
      2. Set the following. Keep it wide so a match is likely:
        • Age: 18 to 35
        • Religion: Hindu
        • Mother tongue: Hindi
        • Diet: Vegetarian
      3. For each, choose whether it is a must-have or flexible, and how much it matters (1 to 3). A must-have removes anyone who fails it. A flexible one only changes the score. Result: an estimate of how many people fit appears. Saving keeps it.
      Use flexible preferences while testing

      Every must-have is a hard filter. A strict must-have, or one that depends on spelling (for example a city), can silently remove the only other person in your test and give you no match at all.

      10.2 Assessments (optional)

      On the dashboard open Assessments and complete one. Answers add to the match score. Leaving them blank is fine but lowers that part of the score to a neutral value.

      11. Member two Part F

      A match needs another person. Repeat the earlier parts quickly for a second member in another private window.

      1. Register Member two as a woman, for example first name Pooja, date of birth 5 May 2002, email pooja@test.com, password Passw0rd-Test2. Confirm the email through the link in Terminal 1 (section 6).
      2. Fill the profile with matching details: Hindu, Hindi, Vegetarian, a city and state, and a bio of 50 or more characters (section 7). Upload a photo and submit.
      3. Admin: approve her profile and photo (section 8).
      4. Verification: upload ID and selfie, then approve it in the admin console (section 9).
      5. Preferences: set age 20 to 40, Hindu, Hindi, Vegetarian, all flexible (section 10). Result: both members now show journey Matching on their dashboards.

      If you do not want to build a second member by hand, the demo members already have approved profiles, photos and IDs. Match Rohan with one of them instead, for example aanya.sharma0@demo.marchmaker.invalid (password DemoPass#2026).

      12. Matching Part G

      Matching is done by the system, then checked and approved by a person. Nothing reaches a member until an admin approves it.

      12.1 How a pair is chosen

      • Who is eligible: an active member with an approved profile, at least one approved photo and an approved ID.
      • Hard filters first: every must-have, in both directions, plus blocks and pairs already rejected.
      • Score from 0 to 1 from three parts: how well each meets the other's preferences (35%), assessments (30%) and life plans such as timeline, children and living arrangements (35%). Members who have waited a long time get a small boost.
      • Cut-off: pairs below 0.55 are not suggested. Each member gets at most 5 suggestions.
      • Members never see the number. They see plain reasons such as “same city” or “similar life plans”.

      12.2 Shorten the waiting time (do this first)

      After an admin approves a match there is an undo window before it reaches the members. It is 10 minutes by default. For testing, make it instant.

      1. In the admin console open Matching settings (the last item in the menu).
      2. In the Review card set Undo window (minutes) to 0 and save.

      12.3 Run matching

      1. Open Match review in the menu and press Run matching now. Result: a summary of how many suggestions were created. Rohan and Pooja should appear as a pair in the list with a score.
      No suggestion for your two members?
      • Open each member's preferences and loosen them. Make sure nothing is a must-have that the other person does not meet.
      • Check both have an approved profile, photo and ID. Without all three they are not in the pool.
      • The pair's score may be under 0.55. Complete an assessment on both, or lower Minimum fit to suggest in Matching settings.
      • Or skip the engine: on the Match review page press Manual introduction. You need each member's ID, which is the long code at the end of their page address under Members in the admin console.

      12.4 Review and approve the match

      1. Open the Rohan and Pooja suggestion.
      2. Read both profiles side by side, the reasons, and the “why we chose them” text. You can edit that text. It is checked for things that are not allowed, such as contact details.
      3. Press Approve (shortcut a) and confirm. Other choices are Reject (r), Snooze (s) and Escalate (e). Result: the match is approved and released. With an undo window of 0 this happens within about a minute, because the worker checks once a minute.

      Some pairs need two different approvers, for example when a member has a past suspension. If that applies, the page says a second reviewer must approve it.

      13. Introduction, credits and chat Part H

      Now both members act. Use each member's own private window.

      13.1 Buy an introduction credit

      Each person needs one credit to say yes. Payment is simulated, so no money moves.

      1. As Rohan open Account, then Billing (/billing).
      2. Under Or buy single introductions, press Buy on one pack. If it asks for a state for tax, choose any state. Result: a message that the payment worked (the page says “Test mode: payments are simulated”) and your credit count goes up by one.
      3. Do the same as Pooja.
      4. Open the invoice from the billing history. It is a printable tax invoice with GST split.

      13.2 Say yes

      1. As Rohan open Your introductions (/introductions). You see one card: the other person's name, age, city and profession, why you were matched, and a blurred photo. You also get a bell notification.
      2. Press Say yes. Pressing Not for me would ask for a reason instead. Result: “You said yes. We will tell you when they respond.” One credit is held, not spent. The page explains that it comes straight back if the other person declines or does not reply in 7 days.
      3. As Pooja open her introductions and press Say yes too. Result: the introduction becomes Connected. Both credits are now spent. More of each person's profile and photos is unlocked.

      13.3 Message each other

      1. Open Messages (/messages) as either member.
      2. Send a first note. It has a minimum and maximum length.
      3. Switch to the other member and reply. Result: your messages appear in the conversation for both people. Contact details are not shared automatically.

      Also try on the introduction: Report and Block (these go to the admin Moderation queue), and, later in the journey, the feedback requests the app sends.

      13.4 Watch it from the admin side

      • Introductions monitor shows every introduction and its state.
      • Payments, Subscriptions and Invoices list the simulated purchases.
      • Audit log records who approved what and when.

      16. If something goes wrong Help

      What you seeWhy, and what to do
      Member site shows “proxy error” or ECONNREFUSED on /api/…The API is not running. Look at Terminal 1. Wait for “api listening”. If it stopped, read the last error.
      API stops with “Invalid environment: …”A .env line is empty or malformed. Delete any NAME= line that has no value.
      API cannot connect to MongoDB (SRV or ECONNREFUSED)Add DNS_SERVERS=8.8.8.8,1.1.1.1 to both .env files. Also check Network Access allows your address, and that the user and password are right.
      “Please confirm your email address to continue”Press resend on that banner, then take the new link from Terminal 1. Real emails are not sent.
      Photo stays on “Processing…”The worker is not running, or the API and worker have different storage settings. Both .env files need STORAGE_PROVIDER=local. Restart Terminal 1.
      Verification upload shows nothingUse a JPEG, PNG or WebP of 2 KB to 8 MB. Look for the green “done” mark rather than the file chooser text.
      Admin asks for an authenticator codeSTAFF_MFA_REQUIRED=false is missing from apps/api/.env, or the API was not restarted after adding it.
      Member site says “Hello, Admin”The browser still has an old shared sign-in. Sign out, or clear site data for localhost, and use private windows for each person.
      No suggestion appears after “Run matching now”See the checklist in section 12.3. Most often: no preferences saved, a strict must-have, or a score under 0.55.
      Nothing reaches the members after approving a matchThe undo window has not ended. Set it to 0 (section 12.2) and wait about a minute. The worker must be running.
      Saying yes shows a “no credit” messageBuy a credit first in Billing (section 13.1).
      Google button is grey with a development noteNo GOOGLE_CLIENT_ID is set. See section 6.5.
      Google says “origin_mismatch” or “access blocked”http://localhost:5173 is missing from the client's authorized origins, or your Gmail is not listed as a test user.
      “Port already in use”An older copy is still running. Close the old terminal windows and start again.
      “Your session could not be verified” (a 403)Refresh the page. If it repeats, clear site data for localhost and sign in again.
